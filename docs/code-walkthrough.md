# Разбор реализации

## 1. Создание события

HTTP-handler разбирает JSON и передаёт данные в `AuditService`.

Service:

1. удаляет лишние пробелы;
2. проверяет обязательные поля и `action`;
3. создаёт UUID и UTC timestamp;
4. вызывает `SaveEventWithOutbox`.

Repository открывает одну PostgreSQL-транзакцию и добавляет:

- полное событие в `audit_log`;
- JSON события в `outbox_events`.

Если любой запрос или commit завершится ошибкой, обе записи откатываются.

## 2. Outbox publisher

Publisher периодически выбирает строки `outbox_events`, у которых
`published_at IS NULL`.

Для каждой строки он:

1. отправляет событие в `user-actions`;
2. использует `user_id` как Kafka key;
3. после успеха заполняет `published_at`;
4. после ошибки увеличивает `attempts` и сохраняет `last_error`.

Если Kafka приняла сообщение, а PostgreSQL не смог отметить его отправленным,
publisher повторит отправку. Поэтому доставка at-least-once, а не exactly-once.

## 3. Analytics consumer

Consumer работает в группе `analytics-group`.

`Setup` и `Cleanup` логируют назначенные и отозванные партиции. Для каждого
сообщения логируются key, partition и offset.

Валидные сообщения накапливаются в batch. Во время flush одна
PostgreSQL-транзакция:

1. добавляет события в `analytics_events`;
2. удаляет события старше текущего часового окна;
3. полностью пересчитывает `stats_cache` из `analytics_events`.

Только после успешного commit PostgreSQL consumer вызывает `MarkMessage` и
ручной `Commit`. Если база вернула ошибку, offsets не двигаются и Kafka сможет
доставить сообщения повторно.

Таймер запускает пересчёт даже при пустом batch. Это удаляет из кэша события,
которые перестали попадать в последний час.

## 4. DLQ

Если сообщение содержит некорректный JSON или неизвестный `action`, оно
публикуется в `user-actions-dlq`.

DLQ envelope содержит:

- исходные topic, key и value;
- partition и offset;
- текст ошибки;
- время обработки.

Offset повреждённого сообщения коммитится только после успешной отправки в DLQ.
Более ранние валидные сообщения сначала сохраняются в PostgreSQL.

## 5. Replay

Replay получает offsets каждой партиции по timestamp и читает диапазон напрямую,
без consumer group.

Поэтому он:

- не меняет offsets `analytics-group`;
- может повторно читать старую историю;
- возвращает агрегаты в HTTP-ответе;
- не заменяет текущий `stats_cache`.

Некорректные исторические сообщения также отправляются в DLQ, а replay
продолжает обработку остальных записей.

## 6. Порядок и пагинация

Kafka producer использует hash partitioner и key=`user_id`. События одного
пользователя попадают в одну партицию и сохраняют порядок внутри неё.

История в PostgreSQL сортируется так:

```sql
ORDER BY timestamp DESC, event_id DESC
```

`event_id` является дополнительным уникальным ключом и не позволяет строкам с
одинаковым timestamp перескакивать между страницами.

## 7. Завершение приложения

HTTP server, consumer и outbox publisher запускаются в отдельных горутинах.
`run()` получает runtime-ошибки через канал, отменяет общий context и ждёт
завершения всех workers через `WaitGroup`.

После этого закрываются Kafka clients и PostgreSQL pool. Ошибка рабочего
компонента возвращается из `run()`, поэтому процесс завершается с ненулевым
exit code.
